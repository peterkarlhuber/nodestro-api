# Nodestro app API contract, version 1 (`nodestro-app/1`)

This contract is what any interface (the embedded web interface, the SDKs, your own frontend) may rely on in any
Nodestro backend: the desktop studio, its network listener, an exported source project and a portable package. All of
them answer the routes below with the same structure. Version 1 is deliberately small: the published workflow API as it
exists, plus discovery (`GET /api/app`) and a form description (`form` in the app info).

The JSON Schemas of the responses are in [`contracts/app-api/v1`](../../contracts/app-api/v1); the contract tests
(`tests/contract/test_app_contract_v1.py`) check every backend variant against them.

## Contract boundary

Exactly these routes belong to the contract. Everything else (`/api/workflows`, `/api/publications`, settings, the
studio's own API, administration) is internal and may change without notice.

| Method and path | Purpose | Schema |
|---|---|---|
| `GET /api/app` | Discovery | `discovery.schema.json` |
| `GET /api/published/{slug}` | App info and form | `info.schema.json` |
| `POST /api/published/{slug}/runs` | Start a run (`?wait=` with `runs.sync`) | `run-status.schema.json` |
| `POST /api/published/{slug}/versions/{n}/runs` | Start a run of release `n` | `run-status.schema.json` |
| `GET /api/published/{slug}/runs` | Latest runs (`?limit=`, `?status=`) | `run-list.schema.json` |
| `GET /api/published/{slug}/runs/{id}` | Run status | `run-status.schema.json` |
| `GET /api/published/{slug}/runs/{id}/result` | Result of a finished run | `run-result.schema.json` |
| `GET /api/published/{slug}/runs/{id}/events` | Progress as Server-Sent Events | `text/event-stream` |
| `POST /api/published/{slug}/runs/{id}/cancel` | Cancel | `run-status.schema.json` |
| `GET /api/published/{slug}/runs/{id}/approvals` | Waiting approvals | `approvals.schema.json` |
| `POST /api/published/{slug}/runs/{id}/approve` | Decide an approval | `run-status.schema.json` |
| `POST /api/published/{slug}/runs/{id}/resume` | Continue a failed run | `run-status.schema.json` |
| `GET /api/published/{slug}/runs/{id}/files` | Result files | `files.schema.json` |
| `GET /api/published/{slug}/runs/{id}/files/{file_id}` | Download a result file | the file |
| `GET /api/published/{slug}/usage` | Runs, tokens and cost (`?days=`) | `usage.schema.json` |
| `GET /api/published/{slug}/openapi.json` | OpenAPI description of this app | OpenAPI 3 |
| `POST /ui/api/session`, `DELETE /ui/api/session` | Sign in and out of the embedded interface | `session.schema.json` |

The pairing routes of a later step (NAL-C4) will join the boundary; they are announced by the capability `pairing`.

Every answer of these routes, errors included, carries the header

```
Nodestro-App-Contract: 1
```

naming the contract version of the answer.

## Discovery: `GET /api/app`

A client calls this first. **Without credentials** the answer is minimal: it never names apps, publications or
versions.

```json
{
  "contract": {"name": "nodestro-app", "versions": [1], "current": 1},
  "backend": {"id": "bk_3f9a0c1b2d4e5f60718293a4", "name": ""},
  "auth": {"methods": ["api_key", "session", "launch_link"]},
  "tls": {"enabled": false}
}
```

**With credentials** (an API key as `Authorization: Bearer ndk_...` or `X-API-Key`, or the embedded interface's
session cookie), the backend adds its versions, the capabilities it serves and the apps that credential may use:

```json
{
  "contract": {"name": "nodestro-app", "versions": [1], "current": 1},
  "backend": {"id": "bk_3f9a0c1b2d4e5f60718293a4", "name": "Office server",
              "version": "0.2.0", "runtime_version": "0.2.0"},
  "auth": {"methods": ["api_key"]},
  "tls": {"enabled": true},
  "capabilities": ["runs", "runs.sync", "events.sse", "files.upload", "files.download",
                   "approvals", "cancel", "resume", "history", "usage"],
  "apps": [
    {"slug": "offer-generator", "name": "Offer generator", "description": "", "release": 3, "languages": [],
     "links": {"info": "/api/published/offer-generator",
               "openapi": "/api/published/offer-generator/openapi.json"}}
  ]
}
```

- `backend.id` is random, created once and kept in the backend's data directory (`instance.json`): stable per desktop
  installation, exported project or portable package. Use it to recognise a backend you have paired with before.
- `backend.name` is chosen by the operator and may be empty: `NODESTRO_BACKEND_NAME` on the desktop, `BACKEND_NAME`
  in an exported project or portable package, or `name` in `instance.json`.
- `auth.methods`: `api_key` (always), `session` (the embedded interface's sign-in, `POST /ui/api/session`),
  `launch_link` (the operator's one-time link of a portable package), `pairing` (reserved, NAL-C4). Ignore methods you
  do not know.
- `tls.enabled`: whether this request reached the backend over HTTPS.
- `apps`: the publications the key is bound to that have an active release (on the network listener: only those
  reachable in the network). A key never learns about other apps.
- An invalid, revoked or expired key answers `401` (`auth.invalid`); a backend never silently treats a wrong
  credential as none.

Discovery is rate-limited like the published API: 120 requests per minute per key, 60 per minute per client address
without credentials (`429 limit.requests` with `Retry-After`); failed authentications count towards the same limit as
on the published API (`429 auth.too_many_failures`).

### Capabilities

Fixed names; a backend lists only those it serves. Clients ignore names they do not know.

| Name | Meaning |
|---|---|
| `runs` | Start runs and read their status |
| `runs.sync` | `?wait=<seconds>` when starting a run; whether an app allows it is `sync.enabled` of its info |
| `events.sse` | `GET …/runs/{id}/events` |
| `files.upload` | Files in a run request (JSON with Base64, or `multipart/form-data`) |
| `files.download` | `GET …/runs/{id}/files[/{file_id}]` |
| `approvals` | `GET …/approvals`, `POST …/approve`; whether an app has approval steps is `approvals` of its info |
| `cancel` | `POST …/runs/{id}/cancel` |
| `resume` | `POST …/runs/{id}/resume` |
| `history` | `GET …/runs` |
| `usage` | `GET …/usage` |
| `notifications` | Reserved (NAL-A3); not served yet |
| `pairing` | Reserved (NAL-C4); not served yet |

## The form: `form` in `GET /api/published/{slug}`

The app info carries the input form in order (`form`) and its version (`form_version`, currently `1`), so a client can
render the form from this one answer:

```json
"form": [
  {"name": "customer", "type": "text", "label": "Customer", "help": "", "required": true, "default": null,
   "options": [], "multiple": false, "accept": [], "accept_formats": [], "max_mb": null, "max_files": null},
  {"name": "kind", "type": "select", "label": "Kind", "help": "", "required": false, "default": "offer",
   "options": ["offer", "invoice"], "multiple": false, "accept": [], "accept_formats": [], "max_mb": null,
   "max_files": null},
  {"name": "documents", "type": "file", "label": "Documents", "help": "", "required": false, "default": null,
   "options": [], "multiple": true, "accept": [".docx", ".pdf"], "accept_formats": ["pdf", "docx"], "max_mb": 10,
   "max_files": 5}
],
"form_version": 1
```

- `type` is one of `text`, `textarea`, `number`, `date`, `boolean`, `select`, `file`. **A client renders a type it
  does not know as JSON input** (later versions may add types without a new contract version).
- Values go into `values.<name>` of the run request; files as `{name, media_type, content_base64}` (one object, or a
  list when `multiple`) or as `multipart/form-data` parts named after the field.
- `accept`: file extensions with their dot (`.pdf`), as an HTML `accept` attribute takes them; `accept_formats`: the
  formats and groups by name as the workflow states them (empty: every supported format); `max_mb`: the largest file;
  `max_files`: the most files (`null`: no own limit).
- An empty `form` means the app takes free text in `input`.

The embedded web interface reads the same mapping (`/ui/api/config`), so there is one form description.

## Errors

Every error of a contract route has one shape:

```json
{"error": {"status": 404, "code": "publication.not_found", "message": "No published workflow with this name",
           "params": {}}}
```

`code` is stable and machine-readable; show your own text for it (the `message` is English and meant for logs). New
codes may appear in any version; treat an unknown code by its HTTP status.

## Versioning rules

- **Additive changes keep the version**: new optional response fields, new capabilities, new authentication methods,
  new error codes, new form field types, new optional request parameters. Clients must ignore what they do not know.
- **Breaking changes need a new major version** (`nodestro-app/2`): removing or renaming a field or route, changing a
  type or meaning, making an optional request field required.
- A backend serves an old major version **at least 12 months** in parallel after a new one appears; `contract.versions`
  lists every version it serves.
- A version that will be removed is announced on its answers with the `Deprecation` header (RFC 9745) and the
  `Sunset` header (RFC 8594) carrying the date after which it may stop answering.
- A client compares `contract.versions` with the versions it supports and uses the highest common one. When there is
  none, it shows "incompatible version" and does not try the routes. A backend older than this contract has no discovery
  (`GET /api/app` answers `404` or something that is not a discovery): a client may fall back to a compatibility
  mode for the published API.
- Backends never refuse silently: a request they cannot serve gets an error answer with a code.

## Not part of version 1

New run endpoints, path changes, RFC 9457 problem details, multi-tenant servers (the contract is shaped so a server can
serve it later unchanged), cross-origin access (CORS), pairing and notifications.
